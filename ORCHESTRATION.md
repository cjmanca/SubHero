# Project Orchestration — Media Metadata & Subtitle Utility

**Scope:** Harness-independent policy for the **main project orchestrator** during benchmark-driven development and, once approved, a project-wide implementation run. These rules apply in any coding-agent harness or direct orchestration session. **They do not apply to delegated implementation/review subagents.** General engineering rules are in [`AGENTS.md`](AGENTS.md).

## Document roles, authority, and access

| Document | Responsibility | Main orchestrator | Delegated agents |
| --- | --- | --- | --- |
| [`docs/00-foundation/`](docs/00-foundation/scope.md), owning feature documents, and [safety invariants](docs/00-foundation/invariants.md) | **Authoritative product requirements**: behavior, safety, supported modes and interfaces | Read only relevant documents for active work | Use owning documents or excerpts supplied in bounded brief |
| [Implementation slice map](docs/40-delivery/implementation-slice-map.md) | Routing to minimal requirements and dependencies | Consult for active slice | Consult relevant slice route if brief allows |
| [Open experiments](docs/40-delivery/open-questions-and-experiments.md) and [benchmark findings](docs/40-delivery/benchmarks/findings.md) | Research questions and observed evidence; **not** approval to treat candidates as requirements | Track measured decisions | Read the relevant focused protocol/findings only |
| [`AGENTS.md`](AGENTS.md) | Assigned implementation/review procedure, permissions and testing discipline | Follow | Follow |
| **`ORCHESTRATION.md`** | Main-orchestrator selection, delegation, acceptance, checkpoint and recovery policy | Read and follow | **Do not read or edit** |
| **`PLAN.md`** *(when approved and created)* | **Immutable** milestone sequence, dependencies, scope and acceptance gates | Read and verify digest; **never edit during execution** | **Do not read or edit** |
| **`STATUS.md`** *(when execution ledger exists)* | **Mutable** progress, tested evidence, blockers, accepted commits, plan digest and next action | Read/update | **Do not read or edit** |
| [`README.md`](README.md) | User-facing overview and navigation | No mandatory engineering role | No mandatory engineering role |

**One owner for each kind of information:** Requirements say **what** the tool must do; `AGENTS.md` says **how scoped work is performed**; this file says **how work is coordinated**; the approved `PLAN.md` says **which gates** must be met; `STATUS.md` says **what has actually been verified**. Product decisions live in [decisions](docs/00-foundation/decisions.md) or their owning feature documents; experiment decisions require measured evidence and a recorded conclusion. Do not duplicate specifications or orchestration rules between files.

**Before a formal implementation plan exists:** The requirements and [benchmark protocols](docs/40-delivery/benchmarks/README.md) are a specification, **not** an implicit authorization to execute every phase. Authorized experimental/benchmark tasks may proceed as bounded work without inventing `PLAN.md` or `STATUS.md`; clearly identify their scope and evidence. Create/freeze a project-wide plan and initialize a status ledger only when their creation/execution is explicitly authorized. Once present, the plan/status rules below are mandatory.

Only the main orchestrator reads or updates `PLAN.md` and `STATUS.md`. A delegated agent gets a self-contained brief, not the project-wide ledger. Harness-specific bootstrap files may link here but must never become another source of coordination policy.

## Main orchestration workflow

1. **Orient:** Re-read this file and `AGENTS.md`; identify the active approved task or plan; consult the slice map, owning requirements/invariants, and relevant benchmark evidence. Inspect `git status`, branch/HEAD, diffs, current source/tests, and any incomplete operations. Reconcile repo state with any status checkpoint; never trust a summary by itself.
2. **Select the next actionable slice:** For a planned implementation run, read `STATUS.md`, choose the **earliest incomplete actionable** slice, and consult its immutable `PLAN.md` acceptance gate and dependencies. Continue independent safe work when a live integration, sample, GPU, or operator prerequisite is unavailable; do not silently jump ahead into a dependent slice. For bounded pre-plan benchmarking, follow only the authorized experiment scope and its protocol.
3. **Delegate carefully:** Give each implementation/review agent a **self-contained brief** specifying outcome, owning document excerpts/links, source paths and boundary, material safety/API/model facts, permitted operations, expected artifacts, acceptance checks, and review focus. **Never send subagents to `PLAN.md`, `STATUS.md`, or `ORCHESTRATION.md`**. Subagents return code, measurements, checks, and findings; the orchestrator owns acceptance and selection of subsequent work.
4. **Run resource-aware and sequentially by default:** Shared local model servers may support only one concurrent request. Do not parallelize subagents, review calls, or GPU jobs unless available capacity/concurrency is explicitly verified and workload isolation is safe. If no independent read-only reviewer is available, conduct a distinct adversarial second-pass review yourself.
5. **Verify and review every slice:** Inspect the actual changes and outputs; run relevant checks. For media-related work, scrutinize permission boundaries, hardlinks, FUSE/multi-filesystem staging, source changes, atomic publication, Plex-visible sidecars, metadata reversibility, subtitle provenance, ASS styling and timing regressions. For benchmark work, challenge unmodified controls, holdout leakage, false positive fixes, denominators, runtime/model version evidence, and any unvalidated algorithm selection. Reviewers report **severity, path/line, impact, reproduction/evidence, and proposed fix**. Fix P0/P1 and gate-blocking P2; retest and re-review affected behavior.
6. **Accept, commit, checkpoint:** Declare a gate passed **only on observed evidence**, never because code exists or an agent claims success. During an authorized planned run, update **`STATUS.md`, not `PLAN.md`**, after an accepted slice, review/fix cycle, milestone determination, or local commit. Record exact checks/results, outstanding findings, blockers, benchmark artifacts/decisions, current branch/commit, and **one concrete next action**. Make focused local commits only after appropriate gates pass; once Docker/bootstrap exists, keep mainline buildable. For pre-plan experiments, write reproducible results in their benchmark artifacts/findings; do not falsely mark unapproved milestones complete.
7. **Continue without routine pauses:** Do not request routine approval between independently authorized slices. After two substantially identical failures diagnose; after three unproductive fix/review attempts document a reproducible blocker and continue unrelated safe work. Never label mocked, synthetic, or offline verification as live acceptance.

## Immutable plan, status ledger, and change control

- **Freeze `PLAN.md` when approved.** It is a versioned contract, not a checklist to tick off. Never edit it to record progress, silently change gates, or unblock implementation. Keep progress and proposed plan changes in `STATUS.md`.
- At plan initialization, record a **SHA-256 of the approved `PLAN.md`** in `STATUS.md`. At startup, after context loss, and before a plan-dependent acceptance decision, compare the current plan digest with the ledger. If the digest differs (or is missing when it should exist), **stop plan-dependent execution** and resolve the discrepancy; do not silently adopt changed plan content.
- When actual changes to milestones, dependencies, or acceptance gates are needed, record a **proposed change with its rationale/impact** in `STATUS.md` and seek user approval for a **new plan version**. Continue unrelated safe work where possible; do not mutate the frozen plan in place.
- When benchmark evidence changes a **technical choice**, create/update a reproducible [benchmark finding/decision](docs/40-delivery/benchmarks/findings.md) and the [open-experiment register](docs/40-delivery/open-questions-and-experiments.md). When a **product requirement** changes, update its owning feature document and [settled decisions](docs/00-foundation/decisions.md) as appropriate. Neither kind of update authorizes unapproved modifications to `PLAN.md`.
- If `PLAN.md` and `STATUS.md` do not yet exist, **do not pretend they do**, generate fake hash checkpoints, or perform project-wide acceptance based on a draft. If only one exists or the ledger cannot be reconciled, mark plan-dependent work blocked until the plan/ledger state is explicitly established.

## Permissions and production-effect safeguards

- Within an authorized implementation run, offline code/document edits, synthetic fixtures, local benchmark runs against read-only samples, mocked integration tests, Docker builds and **local milestone commits** are permitted subject to task scope and available resources.
- **Not implicitly authorized:** Git pushes, remote repository creation/settings/secrets modification, package/image publication, production deployment, cloud inference transmission, live Plex/Tdarr/Bazarr API writes, bulk media modification, enabling unattended apply, or approving operator-only safety gates. A CI workflow describing future publishing does not permit the orchestrator to publish.
- **Never assume media safety from local Docker permissions alone.** In-place MKV metadata edits, external subtitle renames, Plex analysis, Tdarr processing, and user-share writes can have effects outside the container. For live media changes require the specific authorization and safety preflight established in [invariants](docs/00-foundation/invariants.md), [safe media writes](docs/10-media/safe-media-writes.md), and [output/publication rules](docs/20-subtitles/output-and-provenance.md). Do not self-certify operator-only checks.
- Treat reference episodes and private benchmarking annotations as **read-only confidential inputs**. Deliberate corruption must operate on scratch copies. Unapproved generated subtitle files must remain outside Plex-watched folders except an explicitly authorized preview. Never automatically retry an uncertain commit or remote write merely because its initiating process lost context.
- Never treat an unverified upstream Plex selection heuristic, filesystem rename behavior, ASR accuracy claim, model language coverage, or synthetic benchmark result as a verified acceptance gate. Record **EXTERNAL/UNVERIFIED** when real conditions cannot be exercised.

## Context compaction, interruption, and rehydration

**Treat compaction as loss of context, not a completed checkpoint.** This procedure also applies to manual context reset, paused/resumed work, harness migration, and any comparable loss of state. A summary is only a hint; instructions and repository evidence must be reread.

**Before a deliberate reset:** If `STATUS.md` exists for an approved execution run, record the active milestone/slice, last accepted local commit, branch/HEAD, uncommitted changes, exact checks/results, open review findings, blockers, any uncertain in-flight file/API effects, and **one concrete next action**. Mark unfinished work unfinished; never put execution state into `PLAN.md`. For a bounded pre-plan benchmark, preserve the same essentials in its authorized experiment handoff/artifact rather than manufacturing a central status ledger. Do not dump large logs or agent transcripts into checkpoints.

**After reset/resumption, before editing, delegating, committing, or declaring success:**

1. **Restore orchestration policy:** Re-read **`ORCHESTRATION.md` and `AGENTS.md`**. Read a harness bootstrap file only for harness-specific startup behavior, not as product or orchestration authority.
2. **Restore product and experiment boundaries:** Re-read the [safety invariants](docs/00-foundation/invariants.md), the active slice's owning requirements via [the slice map](docs/40-delivery/implementation-slice-map.md), and, for benchmarks, its specific protocol/evaluation criteria. Do not reingest all project docs by default.
3. **Restore frozen plan (if an approved run exists):** Read `PLAN.md` for the active gate; recompute SHA-256 and compare to `STATUS.md`. Stop dependent work on an unexpected mismatch/missing evidence.
4. **Restore execution state:** Read `STATUS.md` for verified progress, unresolved findings, blocker details, and one next action. If no approved plan exists, restore only the authorized bounded experiment/task handoff.
5. **Reconcile actual state:** Inspect `git status`, branch/HEAD, diffs, code/tests, generated benchmark artifacts, and genuinely retained output from prior commands. Correct discrepancies in `STATUS.md` where permitted. **Missing evidence = UNVERIFIED**, never PASS. Detect possibly half-completed writes before considering any replay.
6. **Resume precisely:** Continue the earliest actionable incomplete slice; avoid duplicate implementation, duplicate commits, or reissuing uncertain media modifications/API calls. Delegate via a **fresh, self-contained brief** and keep `PLAN.md`, `STATUS.md`, and this file out of subagent instructions.

If a reset occurred without a usable checkpoint, reconstruct what is possible from source, git history/diffs, artifact manifests, and actual test output; record remaining uncertainty in `STATUS.md` (or the bounded experiment handoff if no ledger exists). **Do not replay any possibly completed media commit or remote operation without first checking its outcome.**

## Completion and handoff

A project-wide implementation milestone is complete only when its **approved `PLAN.md` gate** is satisfied with traceable evidence in `STATUS.md`, P0/P1 and blocking P2 findings are resolved, and the claimed checks actually ran. Benchmark phases also require reproducible artifacts, correctly scoped conclusions, negative-control/regression results, and a decision or explicit *insufficient evidence* outcome; a generated results file alone is not completion.

Treat live Plex/Unraid/Tdarr integration, production media changes, external paid/cloud inference, GitHub releases, and image publishing as **EXTERNAL/UNVERIFIED** unless directly tested with authorization. The final orchestrator handoff must distinguish completed work from deferred/blocked items, include exact verification evidence, state the last accepted local commit if any, and identify the next operator action. Do not claim full application completion merely because the benchmark or offline milestones passed.
