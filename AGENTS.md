# Agent Instructions — Media Metadata & Subtitle Utility

**Scope:** Entire repository, including the benchmark harness, application code, delegated implementers, and read-only reviewers. This file defines **how assigned engineering work is performed**. It is not the product specification, implementation plan, milestone ledger, or main-orchestrator policy. [`README.md`](README.md) is exclusively user-facing.

- Treat `MUST/SHALL` as established requirements, `SHOULD` as agreed direction, and `MAY/OPTIONAL` as selectable/later behavior. `CANDIDATE/TO VERIFY` and example percentages are **not** proven capabilities, calibrated confidence thresholds, or permission to implement untested choices. Where code, upstream claims, experiment results, and requirements disagree, identify the conflict; do not silently weaken product safety.

## Working contract

- Complete assigned, bounded work without routine approval requests. Prefer conservative, reversible choices within the brief and report material assumptions; do not implement adjacent features or speculative frameworks merely because they may be useful later.
- **No fabricated success.** State only checks actually run, observed output, and evidence. Distinguish mocks, offline tests, synthetic fixtures, private-media benchmarks, live integrations, and production deployments. Do not invent model scores, benchmark outcomes, upstream responses, CI results, credentials, or verified platform behavior.
- When sample episodes, model servers, GPU capacity, live integrations, or publishing permissions are unavailable, complete independent offline work and describe the precise blocker. After **two similar failures**, diagnose rather than repeating the same approach; after **three unproductive fix/review attempts**, stop the loop, preserve a reproducer, and return to the orchestrator or continue independent safe work.
- The available inference endpoint may accept only **one request at a time**. **Default to sequential subagents, model requests, and review jobs** unless the actual runtime/resource arrangement is explicitly verified to support concurrency. Do not launch conflicting GPU work merely because tasks appear logically independent.
- Preserve existing work: no force-reset/clean, deletion of unrelated files, silent overwrite, unauthorized commits, or out-of-scope changes. Inspect the actual working tree before changing an interrupted assignment.

## Context compaction and delegated-task recovery

- Following automatic/manual compaction, interruption, or a resumed/migrated assignment, **re-read `AGENTS.md`**, the current **self-contained task brief**, owning feature requirements, applicable invariants, and affected source/tests. For a benchmark, re-read its protocol and scoring contract. A compaction summary is a hint, **not authoritative evidence** of instructions or completed work.
- Re-establish scope, file boundaries, outstanding defects, acceptance checks, and permissions. Inspect affected files, `git status`, and `git diff` to avoid repeating edits or claiming interrupted operations succeeded; rerun only checks that lack verifiable results.
- Before an intentional context reset, give the orchestrator a compact handoff with changed paths, actual commands/outcomes, remaining findings, any uncertain in-flight effects, and **one specific next step**. If the brief is missing or stale, ask the orchestrator for a refreshed scoped assignment rather than guessing project-wide priorities.
- Delegated agents **must not** rehydrate, update, or reconstruct the central `PLAN.md`/`STATUS.md` ledger. The top-level recovery protocol and plan-hash checks live in `ORCHESTRATION.md`.

## Permissions and safety boundaries

- Unless explicitly authorized in the scoped brief, edit only assigned repository files and run local/offline checks. The orchestrator normally owns acceptance, progress records, and local commits; delegated agents do not commit unless specifically delegated.
- **Not implicitly authorized:** Git pushes, publication of packages/container images, creating or changing remote repositories, GitHub settings/secrets, production deployment, enabling unattended media apply mode, live Plex/Tdarr/Bazarr operations, external paid/cloud inference, or writes to the user's actual media library. Writing CI workflows or mocked integration tests is permitted only within task scope; it does not authorize running the resulting release/deployment.
- **Read-only benchmark inputs.** Never mutate reference episodes or their original tracks. Generate controlled corruptions and extracted artifacts in designated scratch space; avoid accidentally putting unapproved subtitle sidecars in Plex-watched directories. Do not check in private media, transcripts, source filenames/paths revealing private collections, secrets, or proprietary model weights.
- For any specifically authorized mutation, follow [safe media writes](docs/10-media/safe-media-writes.md), [output and provenance](docs/20-subtitles/output-and-provenance.md), and [invariants](docs/00-foundation/invariants.md). Protect torrent hardlinks; account for Unraid `/mnt/user`, multiple backing filesystems and concurrent Tdarr changes; stage privately, validate content and source identity, and **commit only with verified atomic publication**. Never delete-then-copy or fall back to a non-atomic overwrite. Cancel/invalidate and requeue when the source changes.
- Distinguish allowed mutation types. Metadata language/forced/commentary correction may be applied when separately authorized. Normal subtitle enhancement creates/replaces an identifiable **generated** track and preserves original subtitle **text**. Retiming existing original tracks is a **separate, opt-in** operation with rollback evidence. Retain ASS styles, fonts, coordinates, layer order, karaoke, animation semantics, and related video streams; do not silently flatten or lossy-reencode. Unapproved proposals remain staged or in the review queue.
- Follow [API/MCP security](docs/30-app/api-mcp-and-security.md): explicit path allowlists, separate API/MCP credentials and ACLs, distinct analysis/approval/commit permissions, and explicit external-provider disclosure/budget rules. No unlimited path access or plaintext secrets in fixtures, logs, or reports. Never assume a remote API operation is side-effect-free just because local code is read-only.

## Bounded implementation and review loop

1. **Inspect:** Read the scoped brief, owning requirements, relevant code/tests, actual versioned upstream documentation, and any more-specific instructions in directories being edited. Identify external side effects and edge cases.
2. **Micro-plan:** Choose the smallest complete change and its measurable acceptance checks. Don't overplan a routine edit or add architecture unrelated to the task.
3. **Implement:** Modify only necessary code/docs. Separate media probing, inference, decision logic, persistence, and publication where it clarifies safety; avoid speculative abstractions.
4. **Verify:** Run focused behavior tests and applicable lint/build checks; inspect actual outputs, including negative controls and failure paths. Never disable safeguards, loosen assertions, or change expected values solely to manufacture success.
5. **Review:** Independently inspect the actual diff against requirements and invariants. A read-only reviewer reports actionable **severity, path/line, impact, reproduction/evidence, and proposed fix**; a review is not a declaration that code “looks fine.”
6. **Fix and recheck:** Correct P0/P1 and acceptance-blocking P2 findings, rerun affected checks, then re-review changed behavior. Record deferred P3 with justification; do not repeat an unproductive loop indefinitely.
7. **Return evidence:** Report changed paths, exact commands/results, unrun/unverified checks, unresolved findings, and the next recommended bounded action to the orchestrator. Do not claim a milestone passed or update central progress records yourself.

**Review severity:** **P0** data loss, credential exposure, security/scope escape; **P1** wrongly modified/published media or tracks, dangerous non-atomic commits, broken core workflow, serious uncontained accuracy regressions; **P2** meaningful reliability or edge-case defects; **P3** cosmetic/optional improvement. Critical/high issues block acceptance. Apply severity to measured impact, not just test count.

## Engineering and testing discipline

- Prefer readable, typed Python, modest dependencies, verified existing libraries, and configured repository tooling. **Do not create Redis/Celery, a generalized test framework, a plugin framework, or extra infrastructure without demonstrated need.** Conversely, persistent queues, web UI, raw API, and MCP *are* established eventual product features; simply do not make the initial algorithm benchmark depend on them.
- Keep the **initial benchmark Python CLI independent** from the eventual application runtime. Use stable, reproducible case manifests, input hashes, tool/model versions, benchmark scripts, and machine-readable outcomes. Do not let experimental results silently select the eventual algorithm; record defensible decisions in [benchmark findings](docs/40-delivery/benchmarks/findings.md).
- Test **changed behavior and consequential failures**, not static reference tables: authorized-root and Docker-path isolation; hardlink, rename and atomic-commit safety; media changes mid-job; subtitle source identity; review/ACL boundaries; queue restart/idempotency; cache invalidation; provenance and rollback; external subtitle naming and collision handling.
- For subtitle processing, cover unchanged-good controls and false positives; original speech versus signs/songs; offsets, gradual drift, discontinuities and individual cues; per-track matching and correlated translations; source-language ambiguity; ASS coordinate/style/layer/animation fidelity; readable fallback when forcing SRT. Spoken duration is **not** the required subtitle display duration.
- For benchmarks, compare on controlled **and** representative real examples, reserve episode-level holdouts, record denominators/uncertainty, count regression and false automatic acceptance, track abstentions/escalations, and separate ASR transcript accuracy from timestamp alignment. Synthetic time shifts are not proof of correct handling of physically cut scenes. Maintain read-only source media and appropriate licenses.
- Tests must be proportional to actual risk. Use focused fixtures and mocked network calls; CI must not require private media, production credentials, model downloads, or live Plex. Avoid tests for trivial data holders/low-value implementation details already exercised by consumer tests.
- Run targeted checks during work, then relevant configured checks (if tools are installed): `python -m pytest -q`, `ruff check .`, `ruff format --check .`, configured type checker, `git diff --check`, and Docker build/smoke tests. Record exact commands/results; report unavailable checks as **NOT RUN/UNVERIFIED**, not passed.
- If adding release or container publishing workflows, verify least-privilege credentials, no secret exposure in untrusted pull requests, coverage of relevant pushes/tags, immutable SHA provenance, `latest` tag race avoidance, and recovery from missed builds. **Workflow code is not permission to publish or deploy.**
- When an experiment genuinely resolves an open technical question, update the [experiment register](docs/40-delivery/open-questions-and-experiments.md) and evidence record. Update the owning requirements file only when product behavior changes; keep project procedure out of the user-facing README.

## Handoff

A delegated task ends with a **concise evidence-based handoff**. The main orchestrator decides whether the acceptance gate passed, updates any authorized execution ledger, and chooses the next slice. Never conceal an unresolved high-severity defect, imply unrun tests passed, or substitute a speculative summary for observed results.
